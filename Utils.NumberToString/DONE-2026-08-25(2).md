# Utils.NumberToString — NTS-05 follow-up: selector configuration, activation caching, effective TimeUnitForms/TimeUnitFormSelectors

Follow-up to `DONE-2026-08-25(1).md` (NTS-05 closure), addressing three review
findings against that PR before merge. The overall `ILexicalFormSelector`
architecture, the Spanish attributive-apocope solution, and the
`ILexicalFormSelector`/`ForcedVariantSet` separation are unchanged — only the
three issues below were fixed.

## 1. Selector-specific XML configuration

A custom selector previously received only its type name and the owning
language identifier (`LexicalFormSelectorConfiguration.TypeName`/
`LanguageIdentifier`) — there was no way for a unit's XML to pass the
selector its own settings (e.g. a plural threshold), short of the selector
reading environment/global state, which the architecture deliberately
forbids.

`LexicalFormSelectorConfiguration` gained a third property,
`Configuration` (an `XElement?`), populated from a new optional
`<LexicalFormSelector type="..."><Configuration>...</Configuration></LexicalFormSelector>`
child element on `<Unit>` (`NumberConvertionConfiguration.xsd`, `<Unit>`
sequence, before `<Forms>`). The core library never interprets
`<Configuration>`'s content — it captures the raw element
(`[XmlAnyElement]` on `LexicalFormSelectorElementType.Configuration`,
converted to `XElement` via `XmlNodeReader`/`XElement.Load`) and hands it to
the selector as-is; the selector owns whatever shape it chooses (attributes,
children, …). The plain `formSelector="..."` attribute keeps working
unchanged and concisely for selectors that need no configuration; it is
ignored when `<LexicalFormSelector>` is present. XSD permissiveness
(`xs:any`/`xs:anyAttribute`, `processContents="lax"`) is scoped strictly
inside `<Configuration>` — nothing else in the schema was loosened.

## 2. Reflection activation caching — per type name, not per instance

The original implementation resolved a type name to a *fully-configured
instance* once and (via the registration dictionary) implicitly could only
represent one configuration per name. That doesn't compose with (1): the same
selector *type* can now be referenced by multiple units, each with its own
`<Configuration>`, so caching a single instance (or a single configured
factory result) per type name would leak one unit's configuration into
another's.

Fixed by caching the expensive part — type/constructor resolution — as a
reusable **activator** (`Func<LexicalFormSelectorConfiguration,
ILexicalFormSelector>`), keyed by type name
(`_lexicalFormSelectorActivatorCache`, a `ConcurrentDictionary`, mirroring
`_registeredLexicalFormSelectors`'s shape). `ResolveLexicalFormSelector` now:
registered name → invoke with this call's `LexicalFormSelectorConfiguration`;
otherwise get-or-build a cached activator for the type name
(`BuildLexicalFormSelectorActivator`, doing `Type.GetType`/assembly
scan/constructor lookup exactly once per distinct type name) and invoke it
with this call's configuration. `Type.GetType`, the assembly scan, and
`GetConstructor` therefore run at most once per distinct selector
*implementation* referenced anywhere in a loaded configuration, not once per
unit — while every unit still gets an instance built from its own
configuration. `RegisterLexicalFormSelector` gained a third, additive
overload, `Func<LexicalFormSelectorConfiguration, ILexicalFormSelector>`, so
a pre-registered name can also honor different per-unit configuration instead
of being locked to one shared instance/factory result. Proven by
`ResolveLexicalFormSelector_SameTypeResolvedTwice_ActivatorCacheGrowsByOneNotTwo`
(cache has exactly one entry after resolving the same type name twice) and
`..._ConstructsANewInstanceEachTime` (constructor still runs on every
resolution — the cache stores the activator, never a shared instance), plus
an end-to-end XML test with the same selector type on two units with two
different `<Configuration>` subtrees producing two different outputs.

## 3. `TimeUnitForms`/`TimeUnitFormSelectors` — corrected to report effective state

A review comment on the original PR was confirmed as a valid, required
correction: `NumberToStringConverter.TimeUnitForms`/`.TimeUnitFormSelectors`
are documented ("Gets the effective ... per time unit ... Always includes at
least singular/plural[/DefaultLexicalFormSelector], synthesized ... when no
explicit override was configured") to return the EFFECTIVE per-unit state,
but the shipped implementation actually returned only explicitly-configured
overrides — a unit with no override was simply absent from both
dictionaries, contradicting the doc comment.

The override-only behavior wasn't arbitrary: it existed to keep
`NumberToStringConverterOptions(NumberToStringConverter source)` (the clone
constructor) safe when a caller narrows `TimeUnits` after cloning — if the
clone constructor copied the *effective* view (every unit, including
synthesized defaults), narrowing `TimeUnits` afterwards would leave stale
`TimeUnitForms`/`TimeUnitFormSelectors` entries for units no longer present,
which the constructor's own validation rejects
(`ArgumentException("TimeUnitForms key '...' has no matching TimeUnits
entry.")`).

Fixed by splitting the single override-only snapshot into two: new internal
properties `TimeUnitFormOverrides`/`TimeUnitFormSelectorOverrides` retain
exactly the old override-only behavior and are the only thing the clone
constructor reads from; the public `TimeUnitForms`/`TimeUnitFormSelectors`
are now computed from `_timeUnits` once it is fully built (same source
`FormatTimeUnit` itself reads), so they report every `TimeUnits` key with its
actual effective `LexicalFormSet`/`ILexicalFormSelector` — synthesized
singular/plural and `DefaultLexicalFormSelector` for units with no override,
the merged result for units with one. Cloning and narrowing `TimeUnits`
remains safe (regression-tested by
`Clone_NarrowingTimeUnits_DoesNotResurrectRemovedUnitFormsOrSelectors`), while
the public contract now matches its own documentation (regression-tested by
`TimeUnitForms_BuiltInEN_ReturnsEffectiveFormsForEveryUnit`,
`TimeUnitFormSelectors_BuiltInEN_ReturnsDefaultSelectorForEveryUnit`,
`TimeUnitForms_ExplicitOverrideOnOneUnit_MergesWithSynthesizedFormsAndSiblingsStaySynthesizedOnly`,
`TimeUnitFormSelectors_OverrideOnOneUnit_SiblingsStillReportDefaultSelector`).
