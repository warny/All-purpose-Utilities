# Utils.NumberToString audit closures — 2026-10-06 (2)

NTS-17 is closed for the round multiples of milione, miliardo and bilione; NTS-15 is narrowed to
its unsourced part; NTS-18 is opened for the remaining Italian domain from a million. Both tickets
were worked together because they share one structural gap: the historical ordinal pipeline
transforms the complete cardinal, whereas these Italian ordinals are built from ordinal constituents
(a scale noun, or two juxtaposed ordinals). Sources and decisions are recorded in
`docs/NTS-08-linguistic-sources.md` ("NTS-15 and NTS-17"), including the ordinal/fraction distinction
(Treccani: `centomillesimoprimo` is the ordinal, `un centomiladuesimo` the partitive; `un milionesimo`
is the fraction, `milionesimo` the ordinal).

Work was test-first: the engine tests did not compile before the primitives existed, and the 24
new positive Italian scenarios and three sweeps were run red (all `NotSupportedException` from the guard)
before the configuration. A before/after dump of every built-in language (cardinals and ordinals
0–2100, thousands multiples, the new 100001–100100 and million-to-10^18 values, `long.MaxValue`,
every variant value, five-minute clock times) was compared after each commit:

| Commit | Changed lines |
|---|---|
| `<OrdinalScale>` / `<OrdinalComposition>` engine | 0 |
| Italian configuration and guard | 57 — IT ordinals only (all previously `NotSupportedException`), no cardinal |

## Engine additions

- **`<OrdinalScale scales multiplierSeparator>`** — the ordinal of a round scale value (multiplier ×
  scale unit, lower groups zero) is built on the singular scale noun (`GetScaleWord`, so
  `<ScaleForm>` applies): multiplier one dropped, a larger multiplier is rendered like its
  standalone cardinal (`ConvertRaw`, then the global cardinal variant rules with `onValue` evaluated
  against the multiplier) + separator + noun. The joined text then goes through the ordinal
  replacements, word rules, stems, `removeTrailing` and the effective variant suffix; the cardinal
  variant rules are not applied to it as a whole. Only the highest scale of the value is considered
  (10^9 is never 1000 × 10^6), found from a static power table. Scale indices must be ≥ 1,
  nameable, reachable by a `long`, and covered by one rule at most.
- **`<OrdinalComposition for divisor separator>`** — head = value − value mod divisor, tail = value
  mod divisor; when both are non-zero the ordinal is ordinal(head) + separator + ordinal(tail). Both
  parts go through the new internal `BuildOrdinalCore` (ordinal plugin, then the declarative
  pipeline, without adjustment, end triggers or finalization), so they receive the same variants and
  may themselves be composed or scale-formed. Termination: both parts are strictly smaller than the
  value, so no depth counter or visited set is needed. `BuildOrdinalFragment` applies the raw
  adjustment and end triggers once, `ConvertOrdinal` the finalization, prefix and sign once. Value
  ranges must be ≥ 1 and pairwise disjoint (no reliance on declaration order); divisor ≥ 2.
- **Precedence** — whole-number exceptions → composition → round scale → historical cardinal-based
  pipeline. Without the new rules nothing changes (dump: 0 lines).
- Shared: additive public records `OrdinalScaleRule` and `OrdinalCompositionRule`, options
  (`OrdinalScaleRules`, `OrdinalCompositionRules`, copied by the clone constructor), converter
  read-only snapshots, DTO (`OrdinalScaleType`, `OrdinalCompositionType`), XSD with
  documentation, `baseOn` (a child declaring rules of a kind replaces that inherited list, because
  overlapping ranges cannot be merged rule by rule). Ranges are parsed and indexed at load; the
  conversion path only reads arrays. Tests: `NumberToStringOrdinalScaleTests`,
  `NumberToStringOrdinalCompositionTests` (formation, recursion, termination, precedence, variants,
  single finalization, plugin interplay, validation, programmatic, snapshot, clone, `baseOn`) and
  two Security immutability tests.

## Italian

- `<OrdinalScale scales="2..4" multiplierSeparator="" />`: `milionesimo`, `duemilionesimo`,
  `diecimilionesimo` (Treccani also accepts `decimilionesimo`), `centomilionesimo`,
  `miliardesimo`, `duemiliardesimo`, `bilionesimo`, feminine `milionesima`. Two ordinal-only
  replacements drop the accent of an inner `tre` (`ventitremilionesimo`, like `ventitremillesimo`).
- `<OrdinalComposition for="1010" divisor="1000" separator=" " />` → `millesimo decimo` /
  `millesima decima`; `<OrdinalComposition for="100001..100009" divisor="1000" separator="" />` →
  `centomillesimoprimo` … `centomillesimonono` / `centomillesimaprima`.
- `ItalianOrdinalLanguageSpecifics` now rejects only zero, 1110–1910 and the other non-round
  thousands above 1999 (NTS-15), the non-round values from a million and every value from a biliardo
  (NTS-18). The NTS-13 forms (1001–1999 synthetic, `milleunesimo`) are unchanged.

## Remaining / opened

- **NTS-15** (narrowed) — 1110–1910 and the non-round thousands above 1999 other than
  100001–100009: no sourced form or spelling.
- **NTS-18** (new) — Italian non-round ordinals from a million, and every ordinal from a biliardo
  (no Treccani entry for `biliardesimo`/`trilionesimo`).

## Test corrections during the work

- The first synthetic test language had no `maxNumber` and was rejected at load ("MaxNumber is
  required for a bounded NumberScale"); `maxNumber` was added.
- Range emptiness was first tested by enumeration, which `IntRange` refuses for an open bound
  (`1..`); it now compares the canonical form.
- A plural test pattern `million(|s)` is not supported by `ToPlural`; it uses `millio(n|ns)`.

## Review fix

- The first version rendered the `<OrdinalScale>` multiplier with `ConvertRaw` only, so the global
  cardinal variant rules (no `onScale`) — applied after `ConvertRaw` for a standalone cardinal — were
  skipped (`two-millionthe` instead of `twa-millionthe` with a feminine `two → twa` rule). The
  multiplier now also goes through `ApplyVariantRules` with the multiplier as numeric value; that
  global pass skips the `onScale` rules already applied inside `ConvertRaw`. Tests run red first:
  `OrdinalScale_Multiplier_AppliesGlobalVariantRules`, `…_AppliesOnValueVariantRules` (both red),
  `…_DoesNotReapplyScaleSpecificVariantRules` (guard against double application). The 73-culture
  dump is unchanged by the fix.
