## NTS-03 — Fixed: composite phrase finalization boundary

Composite conversions now build unfinalized typed fragments and apply language finalization exactly once at the public phrase boundary. Regression coverage includes decimal, `Number`/fraction, currency, year, time/duration, and date composition with a deliberately non-idempotent finalizer.

## NTS-04 — Deferred design limitation

### Decision

**Conclusion A — no concrete defect:** no currently supported built-in language
reproduces NTS-04 as an incorrect output. Keep the limitation documented and
defer the feature. No runtime change is warranted.

The current variant system targets numeric morphology. Surrounding phrase
constituents such as time-unit names, fraction/date-time connectors and
culture-provided month names are not independently variant-aware. Applying
numeric `VariantRules` to the assembled phrase would be incorrect: `OnValue`,
`OnScale`, and replacement scope belong to the numeric fragment and must retain
that fragment's value and context.

### Evidence

- Only EN, FR, and DE define `TimeUnits`; EN-GB inherits the EN units. Their
  configured hour, minute, and second names need only the existing
  singular/plural selection in the phrases generated by the current APIs.
  Existing tests cover single and plural components and multi-component
  durations. German additionally uses `Count1Form="eine"` for all three
  feminine units, while the French `gender=feminin` variant changes the numeral
  in `une heure`. No conflict requiring a different variant per component was
  found.
- Only EN, FR, and DE define `DateFormat`; EN-GB overrides the inherited EN
  pattern. Existing tests cover day 1 and day 2 and observe `July first`,
  `second July`, `premier juillet`, and `ersten. Juli`. Their active variants do
  not establish a requirement to vary a month, first-day literal, or connector.
  Month text continues to come from `CultureInfo.DateTimeFormat.MonthNames`.
- `FractionSeparator` is static in every built-in configuration. Variants are
  forwarded independently to the numerator and denominator numeric fragments.
  Inspection of the built-in variant-bearing languages found no supported API
  case whose separator is grammatically incorrect because it is static.
- `CurrencyDefinition` is supplied by the caller and already lets the caller
  select singular/plural names and a connector appropriate to its context.
  The API makes no promise that those caller-provided strings are inflected by
  numeral variants.
- Named multiplicatives and `MultiplicativeSuffix` are static configuration
  values. No existing built-in multiplicative output demonstrates a need for a
  constituent-level variant.

### Constituent matrix

| Constituent | Variant-aware today? | Existing workaround | Built-in failing case? |
| --- | --- | --- | --- |
| numeral | Yes | `VariantRules` | — |
| ordinal | Yes | `OrdinalVariants` | — |
| time unit | No | singular/plural plus `Count1Form` | None reproduced (EN, FR, DE, inherited EN-GB) |
| fraction connector | No | static configuration | None reproduced |
| date-time connector | No | static configuration | None configured or reproduced in the built-in date languages |
| month | No | `CultureInfo.DateTimeFormat.MonthNames` | None reproduced (EN, FR, DE, EN-GB) |
| currency unit | No | caller-provided `CurrencyDefinition` | None reproduced |
| currency connector | No | caller-provided `CurrencyDefinition` | None reproduced |
| multiplicative suffix | No | static configuration plus named multiplicatives | None reproduced (EN, FR) |

### Existing mechanisms retained

The audit found that the current supported cases are covered by
singular/plural forms, `Count1Form`, `OrdinalVariants`, `FirstDay`,
`FirstCardinalDay`, numeric `VariantRules`, language finalization, and
caller-provided `CurrencyDefinition` values. None should be replaced merely to
make the model more uniform.

Do not generalize the phrase model until a concrete supported-language
requirement demonstrates that these mechanisms are insufficient. In
particular, do not add a generic phrase-token model, run `VariantRules` over the
final phrase, or use `FinalizeWriting` as a generic constituent-inflection
hook. If a future red test proves a need, extend only the affected constituent
and preserve the existing variant validation, precedence, and inheritance
semantics.

## Closed / superseded historical findings

- NTS-01: External/user-supplied configurations are schema-validated before deserialization. Built-in configurations use the same secure parsing and semantic-validation pipeline but skip runtime XSD validation because the complete built-in resource set is schema-validated by unit/CI tests.
- NTS-02: Built-in initialization is isolated per configuration document. A failing built-in no longer escapes the static initializer or prevents independent valid built-ins from loading. Failures are retained as initialization diagnostics, while built-in XSD and semantic validity remain CI/release invariants.

- Items 47–61: resolved in current code/history (signed numeric boundaries, exact currency arithmetic, regex timeout, configuration validation, transactional registration, inheritance-cycle/presence handling, variant strictness/precedence, language-specifics registration, strict culture lookup, etc.).
- Pass-2 items 62–64 and 66–73: resolved or intentionally documented.
- Pass-4 item 92: superseded by the internal presence-aware `LanguageDefinition` / `Optional<T>` model. Explicit zero/false and absent values are no longer conflated for the presence-sensitive fields.
- Pass-4 item 95: fraction-key validation is implemented; generic "all digits must exist" validation remains intentionally deferred because partial digit fixtures/configurations are supported by the current model.
- Historical Zulu/Arabic/Greek/Slavic agreement notes are linguistic-model limitations, not regressions to fix speculatively.
