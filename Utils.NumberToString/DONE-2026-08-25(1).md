# Utils.NumberToString — NTS-05 closure: extensible lexical form selection + Spanish attributive apocope

Closes NTS-05. Resolves the Spanish time-unit deferral recorded in
`DONE-2026-08-24(1).md` (2026-08-24) — that deferral is not being rewritten as
wrong: at the time, Spanish attributive apocope genuinely could not be
expressed correctly with `gender` + `ForcedVariants` + `Count1Form` alone, and
deferring rather than shipping `"veintiuno minutos"` was the right call. This
PR adds the missing capability.

## Problem

The time/unit lexical model was `Singular` / `Plural` / `Count1Form` — a
binary `count == 1 ? Singular : Plural` choice. Two genuinely different
grammatical mechanisms were being asked to share this one model:

- **`ForcedVariants`** (NTS-04): a lexical constituent constrains the
  morphology of the NUMBER it governs (e.g. French "heure" forces
  `gender=feminin`).
- **Lexical form selection** (new, NTS-05): the numeric value/context
  determines which FORM OF THE UNIT WORD is used (e.g. future Russian
  "час"/"часа"/"часов").

These are related but distinct, and conflating them into `Singular`/`Plural`
cannot express languages where either axis needs more than two states.

## Resolution — `ILexicalFormSelector`

- `ILexicalFormSelector.SelectForm(LexicalFormContext)` (`ILexicalFormSelector.cs`)
  returns a FORM KEY only (e.g. `"singular"`, `"plural"`, `"one"`, `"few"`,
  `"many"`) — never the localized word. Implementations must be
  stateless/thread-safe after construction; `SelectForm` is the only member
  ever called on the conversion hot path.
- `LexicalFormSet` (`LexicalFormSet.cs`) is the word-side counterpart of
  `ForcedVariantSet`: an immutable form-key → localized-word map, mirroring
  its `Empty`/`Create(params IEnumerable<(string,string)>)` shape and
  `NumberToStringConfigurationException` validation (`UNTS007`).
- `DefaultLexicalFormSelector` reproduces today's exact behavior
  (`AbsoluteValue == 1 → "singular"`, else `"plural"`) and is used
  automatically for every unit that configures no selector — legacy
  Singular/Plural-only configurations (EN, DE, FR, PT, GL, CA) are unaffected,
  confirmed by running the full suite before touching any language XML.
- Custom selector resolution (`NumberToStringConverter.RegisterLexicalFormSelector`/
  `ResolveLexicalFormSelector`) mirrors the existing `RegisterLanguageSpecifics`/
  `ResolveLanguageSpecifics` precedent exactly: explicit registration first,
  then `Type.GetType` + assembly scan, then instantiation via a
  `(LexicalFormSelectorConfiguration)` constructor if declared, else
  parameterless. Resolution happens once, in `ReadConverter`, during
  configuration loading — never from `Convert(...)`. Unlike the
  `LanguageSpecifics` precedent (which throws plain `InvalidOperationException`),
  failures use `NumberToStringConfigurationException` with error code
  `UNTS008`, consistent with the rest of the NTS-04/05 diagnostic family.
- `TimeUnitDefinition` (internal) gained `Forms`/`Selector`; `FormatTimeUnit`
  now computes the effective query (`ForcedVariants.Overlay(...)`), asks the
  selector for a form key, resolves the word via `Forms.TryGetForm`, and
  raises `UNTS007` if the selector returns a key the unit doesn't configure.
  `Count1Form` remains a distinct, literal override for count == 1 — untouched.
- Public API: `NumberToStringConverterOptions.TimeUnitForms`/
  `TimeUnitFormSelectors` (additive, mirroring `TimeUnitForcedVariants`) and
  `NumberToStringConverter.TimeUnitForms`/`TimeUnitFormSelectors` (read-only,
  non-default entries only — cloning a converter and narrowing its `TimeUnits`
  never resurrects a stale override for a removed unit). The existing
  `TimeUnits` tuple property is completely unchanged.
- XML: optional `formSelector="..."` attribute and `<Forms><Form key="" value=""/></Forms>`
  child on `<Unit>`, purely additive to the XSD — every existing `<Unit>`
  across every built-in language remains valid unchanged.
- No culture-specific branches, no post-render string replacement, no new
  finalization boundary (`NumberToStringCompositeFinalizationTests` covers a
  custom selector explicitly).

## Spanish — solved with zero new runtime code

Spanish attributive apocope (`uno`→`un`, `veintiuno`→`veintiún`, `treinta y
uno`→`treinta y un` before a masculine noun) turned out to be a
**`ForcedVariants` problem, not a lexical-form-selector problem**: "hora" only
ever needs its ordinary singular/plural word forms — what varies is the
NUMERAL's grammar, not the unit word. `ILexicalFormSelector` is not used by
Spanish at all; it is proven only by synthetic/custom tests.

`NumberConvertionConfiguration.ES.xml` adds one new `VariantDimension`,
`form` (`standalone` | `attributive`, default `standalone`), and one nested
`<Variant type="gender" variant="masculino"><Variant type="form" variant="attributive">`
rule (`uno`→`un`, `veintiuno`→`veintiún`) — reusing the exact nested-`<Variant>`
combination mechanism already proven by German's `gender`×`case` rules
(`NumberConvertionConfiguration.DE.xml`). Time units force
`form=attributive` (`hour` also forces `gender=femenino`); ordinary
`Convert(...)` calls never do, so `form` defaults to `standalone` and
apocope never leaks into ordinary cardinals. No `Count1Form` is needed
anymore for `minuto`/`segundo`: the same generic mechanism now covers
count == 1 and compound counts (21, 31, …) uniformly.

```
es.Convert(21)                        -> "veintiuno"        (standalone: unaffected)
es.Convert(TimeSpan.FromHours(21))    -> "veintiuna horas"  (hour forces gender=femenino,form=attributive)
es.Convert(new TimeSpan(0,21,0))      -> "veintiún minutos" (minute forces form=attributive; gender defaults masculino)
```

### Side effect discovered and fixed: ordinal default-form resolution requires full dimension coverage

Adding a second `VariantDimension` to a language broke Spanish's existing
`<Ordinals>` section: `ParseOrdinalVariants`'s `SelectDefaultForm` requires an
`OrdinalException`/`Ordinal` entry that relies on the FormVariants default
fallback (no explicit top-level `string=`/`to=`) to have a candidate whose
constraint count exactly equals the number of *all* declared dimensions —
not just the ones it explicitly mentions. Spanish's ~47 ordinal entries use
the compact `<Variant type="gender" forms="X,Y"/>` shorthand and previously
relied on that implicit default-form fallback, which now needed to also
account for `form`.

This is not a bug introduced by NTS-05: German's ordinals already establish
the working convention for this exact requirement — every `OrdinalException`/
`Ordinal` in `NumberConvertionConfiguration.DE.xml` nests all three of its
dimensions (`gender` × `declension` × `case`) explicitly. Retrofitting the
same nesting into 47 Spanish entries (purely to satisfy a dimension Spanish
ordinals don't care about) would have been a disproportionately large,
semantically noisy change for an ordinal system that has no
attributive/standalone distinction at all. Instead, every Spanish
`OrdinalException`/`Ordinal` now carries its already-known masculine/default
form directly as a top-level `string=`/`to=` attribute (e.g.
`<OrdinalException value="1" string="primero">`), which is the value the
default resolver would have produced anyway. This makes `needsDefault` false
for every entry, so the resolver's exhaustive-dimension check is never
reached — while runtime gender-specific ordinal dispatch (`OrdinalVariants`,
ordinary subset matching, unaffected by this) is completely unchanged. All
pre-existing Spanish ordinal tests remain green.

## Deliberately deferred (design, not implementation)

Per scope: only the extensible infrastructure and the Spanish production case
are implemented. Full multi-form plural systems remain future work:

- **Russian, Ukrainian, Polish, and other Slavic languages**: count-dependent
  noun-form selection (`час`/`часа`/`часов` for 1 / 2–4 / 5+). The
  architecture already supports this — `NumberToStringConverterLexicalFormSelectorTests.Convert_Synthetic_ThreeFormSelector_SelectsBeyondSingularPlural`
  proves a selector returning three distinct keys (`"one"`/`"few"`/`"many"`,
  intentionally synthetic — not a real language's rule) works end-to-end
  through `TimeUnitForms`/`TimeUnitFormSelectors`. `ForcedVariants` remains
  responsible for any independent numeral gender agreement (`один час` /
  `одна минута`); a real CLDR-style plural-category selector is a follow-up.
- **Arabic and other dual/paucal/plural-category languages**: same class of
  gap, same architecture applies without redesign.
- **Italian** elision (`un'ora`) was audited and intentionally not attempted:
  it is not representable by the current lexical/numeral primitives without
  new machinery, and a superficially-plausible but linguistically wrong form
  was rejected.

## Regression coverage

- `NumberToStringConverterLexicalFormSelectorTests.cs` (new): `DefaultLexicalFormSelector`
  direct tests; `LexicalFormSet` validation; `ResolveLexicalFormSelector`
  registered-instance/registered-factory/reflection-by-assembly-qualified-name/
  config-aware-constructor paths; deterministic `UNTS008` failures (type not
  found, doesn't implement the interface, instantiation fails); the synthetic
  three-form selector; runtime `UNTS007` when a selector requests an
  unconfigured key; a custom selector loaded through the real
  `NumberToStringConverter.ReadConfiguration` XML pipeline (not just
  programmatically); `TimeUnitForms` immutability/snapshot.
- `NumberToStringConverterESTests.cs`: 1/21/31 × hour/minute/second, a
  composite `21h21m21s` proving independent feminine-hour and
  masculine-attributive-minute/second contexts don't leak, and unchanged
  ordinary-cardinal regression (`uno`/`veintiuno`/`treinta y uno`).
- `NumberToStringCompositeFinalizationTests.cs`: one new test proving a
  custom `ILexicalFormSelector` on a time unit is still finalized exactly
  once (NTS-03 preserved).
- Full `NumberToString`-filtered suite (920 tests) run before and after the
  `TimeUnitDefinition`/`FormatTimeUnit` refactor and again after the ES.xml
  change, confirming EN/DE/FR/PT/GL/CA time output and all existing Spanish
  cardinal/ordinal/currency tests are byte-for-byte unchanged.

## Status

NTS-01 through NTS-04 remain closed as previously recorded. NTS-05 is closed
via the general `ILexicalFormSelector` mechanism described above, plus the
additive Spanish attributive-apocope fix built entirely on the existing
`ForcedVariants` engine. `TODO.md` carries no open item for
`Utils.NumberToString`.
