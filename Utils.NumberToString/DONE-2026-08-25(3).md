# Utils.NumberToString — NTS-05 follow-up: selector resolution reuses Utils.Collections.CachedLoader

Second follow-up to `DONE-2026-08-25(1).md`/`DONE-2026-08-25(2).md` (NTS-05
closure and its first review round). This round is scoped to a single
concern raised on re-review: selector activation caching duplicated
infrastructure that already exists in the repository, instead of reusing it.
The overall `ILexicalFormSelector` architecture, selector-specific XML
configuration, `ForcedVariants`/lexical-form separation, effective
`TimeUnitForms`/`TimeUnitFormSelectors`, Spanish's attributive handling, and
legacy singular/plural behavior are all unchanged.

## Problem

The previous round introduced a bespoke pair of registries in
`NumberToStringConverter.Globalization.cs`:

- `_registeredLexicalFormSelectors` — explicit `RegisterLexicalFormSelector`
  registrations.
- `_lexicalFormSelectorActivatorCache` — reflection-resolved activators,
  keyed by type name, consulted only after the first dictionary missed.

Two competing `ConcurrentDictionary`-backed registries for what is
conceptually one lookup (`"how do I get an activator for this type name?"`)
duplicated caching logic the repository already has in
`Utils.Collections.CachedLoader<TKey, TValue>` — a general-purpose,
`IDictionary`-shaped cache that loads a value on first miss via a supplied
`TryLoadValueDelegate` and reuses it afterwards.

## Resolution — one CachedLoader-backed registry

`_lexicalFormSelectorActivators` (a single
`CachedLoader<string, Func<LexicalFormSelectorConfiguration,
ILexicalFormSelector>>`) replaces both prior dictionaries:

- **Explicit registrations** (`RegisterLexicalFormSelector`, all three
  overloads) now write directly into the cache
  (`_lexicalFormSelectorActivators[typeName] = activator;`), bypassing the
  loader entirely — registrations therefore always take precedence over
  reflection, by construction, not by an `if` check ordering two registries.
- **The built-in `"default"` alias** is preloaded the same way, at cache
  construction (`CreateLexicalFormSelectorActivatorCache`), through the exact
  same `cache[key] = activator` mechanism a future built-in (a CLDR or
  modulo-range selector, explicitly out of scope for this PR) would use.
  `ResolveLexicalFormSelector` no longer special-cases the string
  `"default"` — only the (unavoidable) null/blank fast path remains, since
  there is no key to look up when no selector was configured at all. One
  minor, deliberate behavior narrowing: the alias match is no longer
  case-insensitive (`"Default"`/`"DEFAULT"` are no longer recognized) — this
  was untested, undocumented, and not exercised by any built-in
  configuration; the documented alias is `"default"` exactly.
- **Unregistered type names** fall through to the loader,
  `LoadLexicalFormSelectorActivator` — the same `Type.GetType`/assembly-scan/
  constructor-lookup logic as before, now shaped as a
  `CachedLoader.TryLoadValueDelegate` (`(string, out Func<...>) => bool`)
  rather than a private helper called manually from `ResolveLexicalFormSelector`.
  A resolution failure throws `NumberToStringConfigurationException`
  (`"UNTS008"`) instead of returning `false`, so it is never cached — a later
  attempt for the same bad type name retries reflection from scratch, exactly
  as before.

`ResolveLexicalFormSelector` itself shrank to: null/blank → default selector;
otherwise, build the `LexicalFormSelectorConfiguration` and index the cache
(`_lexicalFormSelectorActivators[typeName]`, which loads-and-caches on miss),
then invoke the returned activator with that configuration, wrapping any
*activation* failure (e.g. a selector constructor throwing for this specific
unit) as `UNTS008` with the caller's language identifier. Net effect: less
code than before, one registry instead of two, same public behavior.

## Concurrency — documented honestly, not oversold

`CachedLoader`'s non-`Dictionary` backing-store path (used here, since the
holder is a `ConcurrentDictionary` for thread safety) is a plain
check-then-load-then-store sequence, not an atomic `GetOrAdd`. Under a race,
the reflection loader can therefore run more than once for the same
not-yet-cached type name before the cache converges to one entry. This is
harmless — `LoadLexicalFormSelectorActivator` is deterministic and
side-effect-free, so a redundant run produces an equivalent activator, and
every caller still gets a correctly-configured selector — but it is a weaker
guarantee than "the loader runs at most once, ever," and the previous
`ConcurrentDictionary.GetOrAdd`-based implementation didn't claim a
meaningfully stronger one either. Doc comments on
`_lexicalFormSelectorActivators`/`ResolveLexicalFormSelector` and the
README's "Lexical form selection" section now state this precisely instead
of implying a stronger single-execution lock. No additional locking was
added around `CachedLoader` — none is needed for correctness, only for
avoiding (harmless, rare) redundant reflection work, which isn't worth the
complexity.

## Removed: cache-count test instrumentation

`NumberToStringConverter.LexicalFormSelectorActivatorCacheCount` (an
`internal static int` added solely so a test could assert on cache entry
count) is removed — production code no longer exposes cache-internals state
for tests to inspect. The two tests that depended on it are gone.

## Test fixes — deterministic, order-independent, requirement-mapped

The removed tests were order-dependent: they compared the shared,
process-wide activator cache's size *before* and *after* resolving a type,
which only holds if no earlier test (running in an unspecified MSTest order)
already resolved that same type name. Replacements are self-contained —
each either resets its own test-local static counter immediately before
asserting, or asserts purely on returned-instance identity/behavior, never
on shared cache state:

- `ResolveLexicalFormSelector_SameTypeResolvedTwice_ConstructsANewInstanceEachTime`
  (kept, now uses a renamed, single-purpose `ConstructionCountingSelector`):
  proves the cache stores an activator, not a shared instance — two
  resolutions of the same type still construct two distinct instances.
- `RegisterLexicalFormSelector_ConfigAwareFactory_ReceivesPerUnitConfigurationAndTakesPrecedenceOverReflection`
  (new): proves the configuration-aware `Register` overload both takes
  precedence over reflection (registered under a name that isn't a real
  type) and receives each call's own `LexicalFormSelectorConfiguration`
  (language identifier and `<Configuration>` content) independently.
- `Convert_ReflectionResolvedSelector_ConstructsSelectorOnceAtConfigurationLoadNotOnEachConvertCall`
  (new): loads a converter via the real XML pipeline with a
  construction-counting reflection-resolved selector, asserts the
  constructor ran exactly once after `ReadConfiguration`, then calls
  `Convert` five times and asserts the count is still exactly one — a
  concrete regression guard for "no reflection on the conversion hot path,"
  not just an architectural claim.
- Discovery-caching itself (the performance characteristic that
  `Type.GetType`/assembly-scan/`GetConstructor` run at most once per type
  name) is delegated to `CachedLoader`'s own contract rather than
  re-verified via cache-internals introspection; its functional consequence
  — the same type name reused correctly, without cross-contamination, across
  units with different configurations — remains covered by
  `ReadConfiguration_SameSelectorTypeWithDifferentConfigurationsOnTwoUnits_EachUsesItsOwnConfiguration`
  (unchanged from the previous round).
- Existing `ResolveLexicalFormSelector_RegisteredInstance_IsUsed`/
  `..._RegisteredFactory_IsInvoked` comments now spell out explicitly why
  they already prove precedence over reflection (the registered names aren't
  real type names, so a reflection fallback would fail instead of silently
  succeeding).

Net test count: 27 in `NumberToStringConverterLexicalFormSelectorTests.cs`
(26 − 2 removed + 3 added), all deterministic and independent of execution
order. Full `NumberToString`-filtered suite: 931/931.

## Unchanged (explicitly verified)

- `ILexicalFormSelector`, `LexicalFormContext`, `LexicalFormSet`,
  `LexicalFormSelectorConfiguration` — no changes.
- `<LexicalFormSelector type="..."><Configuration>...</Configuration></LexicalFormSelector>`
  XML shape and the plain `formSelector="..."` attribute — no changes; both
  still resolve through the same registry.
- Spanish (`NumberConvertionConfiguration.ES.xml`) — untouched; still uses
  only `ForcedVariants`' `form=standalone|attributive` dimension, no lexical
  form selector. `21 → veintiuno`, `21 horas → veintiuna horas`,
  `21 minutos → veintiún minutos`, `31 minutos → treinta y un minutos`
  reconfirmed by `NumberToStringConverterESTests`.
- `TimeUnitForms`/`TimeUnitFormSelectors` effective-view correction from the
  first review round — untouched; this round only changed how the
  *selector* is resolved and cached, not how forms/selectors are exposed.

## Status

NTS-05 remains closed; this round is a targeted infrastructure-reuse
correction with no XML/API surface change. `TODO.md` carries no open item
for `Utils.NumberToString`.
