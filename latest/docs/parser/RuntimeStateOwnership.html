Runtime State Ownership

This document is the canonical ownership and authority reference for the current runtime. It is conservative, documentation-only, and describes current contracts only.

Runtime authority model (current contract)

  • ParserEngine owns final parse acceptance.
  • ParserEngine owns final diagnostics.
  • ParserEngine owns final parse-tree outcome.
  • AlternativeScheduler is orchestration-only and does not own global parse success/failure.
  • ScheduledAlternativeExecutor is local and non-authoritative.
  • ParserStateRegistry is parse-lifecycle-scoped storage and does not own final parse acceptance.
  • ActiveParseState is descriptive state and is not a runtime invocation frame.

Supported runtime ownership semantics

Current supported ownership contracts are:

  • deterministic syntax-oriented parsing with ParserEngine as final authority;
  • non-authoritative orchestration and metadata transport;
  • advisory lookahead plus parser-authoritative fallback;
  • invocation-local registry lifecycle and deterministic reuse boundaries;
  • metadata-only continuation/shared-prefix/lookahead observability.

For unsupported semantics and compatibility interpretation (including parseable/observable boundaries), see ParserMetadataAndRuntimeLimitations.md.

Parsing, scheduling, and local execution boundaries

Parsing authority

ParserEngine remains authoritative for:

  • recursive rule parsing decisions,
  • branch acceptance/rejection,
  • trailing-token validation,
  • final parse materialization.

Scheduling authority

AlternativeScheduler:

  • coordinates deterministic ordering and local candidate comparison,
  • can aggregate observability metadata,
  • does not own global parse success/failure,
  • does not own diagnostics authority.

ScheduledAlternativeExecutor:

  • performs local attempt execution,
  • can use lookahead for deterministic local reject evidence only,
  • cannot accept a branch from lookahead-only outcomes,
  • cannot finalize parse acceptance.

Lookahead authority boundaries (ownership view)

Lookahead is advisory and non-authoritative.

  • lookahead cannot independently finalize parse acceptance;
  • lookahead cannot independently finalize diagnostics authority;
  • lookahead cannot accept a branch;
  • non-reject lookahead outcomes require real parsing;
  • no adaptive parsing exists in the current runtime.

ImmediateReject may be used only as deterministic local reject evidence in allowed contexts. RequiresParse, Unknown, and EpsilonPossible require parser-authoritative execution.

For conceptual fallback lists and limitations detail, see ParserMetadataAndRuntimeLimitations.md.

ParserStateRegistry lifecycle ownership

ParserStateRegistry owns parse-lifecycle-scoped runtime storage for:

  • visited parser-state tracking,
  • invocation-local continuation transport metadata,
  • invocation-local completed results,
  • deterministic reusable completion selection inputs.

Boundaries:

  • Clear() resets registry-owned state for a new parse lifecycle; ParserEngine.Parse clears it both when a parse starts and when it ends (successfully, with an ErrorNode, or with an exception), so no parse state outlives its parse (S-06); a collection that held more than ParserStateRetention.MaxRetainedEntries (1,024) entries is also shrunk, so a reused engine does not keep the capacity of its largest parse;
  • every insertion of a new visited state, continuation, completed result or look-ahead entry is charged to the running parse's MaxRetainedStates budget before it is stored; an exhausted budget refuses the whole parse instead of dropping or evicting an entry;
  • reusable results are invocation-local completion artifacts;
  • reusable result selection is not final parse acceptance;
  • invocation reuse != execution reuse;
  • current memoization is syntax-oriented and non-semantic;
  • semantic evaluator external state is not modeled by memoization keys;
  • parser action side effects are not modeled by memoization keys.

Registry usage audit and compact storage (registry-metadata audit)

Verified producers and consumers of the three registry collections on 6e7892a0 (line numbers on that commit). No other assembly reaches the registry: it is internal, and InternalsVisibleTo names only the Unit and Security test projects. No runtime observer, invocation-frame manager, rule-call policy or lifecycle executor receives registry data.

All three live for one parse: ParserEngine.Parse clears them when a parse starts and when it ends (ParserEngine.cs:360, :374), and every call of a CompiledGrammar owns its engine. Custom policies reach the registry only through IParserExecutionStateManager: GetCurrentStateKey() is part of every RuleInvocationKey (memoization and continuation identity) and Capture() provides the snapshot stored with each completed result.

In production the engine stores at most one result per invocation key: a key is stored only after a memo miss, a re-entrant call of the same key is stopped by _activeRuleFrames before it stores anything, and every stored result is reusable (IsFailure == (Node is null)). Every key recorded as a visited state has ElementIndex == AlternativeIndex.

Since the registry-metadata audit the storage is compact but exact (ParserStateRegistry remarks):

  • visited states with ElementIndex == AlternativeIndex and an alternative index in [0, 63] are grouped by (rule, position, precedence) with one bit per alternative; any other key goes to an overflow set of full keys;
  • continuations are one flat set of (invocation, continuation) pairs instead of one set per invocation;
  • completed results keep their first result inline, with an overflow list allocated only for later results of the same key (direct registry callers).

Membership, duplicate detection, the insertion order of completed results, reuse preference, snapshots and therefore every S-06 charge and refusal are those of the historical sets and lists; the historical storage is kept as a reference model in ParserStateRegistryBudgetTests. Measurements: ParserResourceSafety.md section 9.

GetContinuations returns the exact set of distinct continuations of an invocation, in an unspecified order. No production code reads it, the historical per-invocation HashSet did not guarantee an order either, and the tests compare continuations as sets (including heavily interleaved invocations with duplicates). Completed results, read by the memoization, keep a guaranteed insertion order because the reuse preference (first success, then first failure) depends on it.

Operation ownership and concurrent use (issue #709)

A CompiledGrammar separates what one grammar shares from what one operation owns. Every Tokenize(string) and Parse(string) call creates its own LexerEngine and ParserEngine; the grammar-invariant tables those engines need are built once by the CompiledGrammar constructor (internal LexerEngine.Preparation and ParserEngine.Preparation) and are never mutated afterwards.

Before #709 a CompiledGrammar owned one engine pair, and every call reset the shared engine state: ParserEngine.Parse cleared _activeRuleFrames, the state registry and the look-ahead cache at its start and end, and LexerEngine.Tokenize reset the mode stack and pending more text. Concurrent calls therefore cleared or reused each other's state: a memoized completed result computed for another input could be selected as a reusable result (silent wrong tree or wrong branch selection), visited-state and frame guards could reject or accept alternatives for another input (wrong acceptance), a mode switch of one tokenization could apply to another (wrong tokens), and concurrent writes to the non-thread-safe collections could corrupt them permanently (exceptions and wrong results even after the concurrent phase).

Contract:

  • CompiledGrammar.Tokenize and CompiledGrammar.Parse may be called concurrently on one shared instance, and re-entrantly (for example from a lexer action or a predicate of another call on the same grammar), when the runtime policy is ParserRuntimeFeaturePolicy.Default or another policy whose components are stateless or thread-safe;
  • the components of ParserRuntimeFeaturePolicy.Default keep no instance state;
  • policy components are never cloned; a custom component with mutable state (for example StackParserRuleInvocationFrameManager, a recording observer, or a policy bound to a generated execution context) is shared by every call of the grammar, so concurrent use of such a grammar is supported only when the caller guarantees the component is thread-safe; otherwise one CompiledGrammar per concurrent operation is required;
  • a directly constructed LexerEngine or ParserEngine remains non-thread-safe and non-re-entrant; several LexerEngine.Tokenize enumerations of one engine may however be interleaved on one thread or abandoned, since each owns its mode stack and pending more text;
  • the CSyntax/VBSyntax front ends inherit the guarantee: CSyntaxTokenParser, VBSyntaxTokenParser, CSyntaxExpressionCompiler and VBSyntaxExpressionCompiler keep no mutable instance state (a compilation builds its own ParseTreeCompiler and compilation context), so one instance may serve concurrent calls; an ExpressionCompilerContext or VBSyntaxCompilerContext passed explicitly to CompileExpression is read and mutated by that compilation and must not be shared by concurrent compilations;
  • no lock, thread-local engine or pool is used; resource budgets stay owned by each operation (S-06).

Engine reuse and retained memory (engine-reuse audit)

The engine-reuse study deferred by #709 considered three strategies: fresh engines per call, a bounded per-grammar engine pool, and immutable caches extracted from the engines. Only fresh engines and a directly reused engine were measured; no pool prototype was built or benchmarked, and the immutable grammar-invariant data is already extracted into the shared preparations. Fresh engines are kept and the pool is abandoned on design grounds: a pooled engine would by construction keep the capacity of the largest parse it served, which is exactly the retention this audit removed, while the cost of fresh engines measured for #709 is an allocation overhead of 12–19 % on parse.

Retention guarantees, for a long-lived CompiledGrammar (a generated static Grammar, the CSyntax/VBSyntax shared grammars) and for a reused engine:

  • the input text is unreachable from the grammar and its engines once Tokenize or Parse returns, and from a LexerEngine once an enumeration completes or is disposed (the diagnostic LastResourceBudget no longer reaches the reader);
  • the per-parse collections of a ParserEngine (_activeRuleFrames, visited states, continuations, completed results, look-ahead entries) are emptied after every parse and shrunk when they still held more than 1,024 entries at that point; smaller ones keep their capacity, so sequential reuse on ordinary inputs does not regrow them. The decision uses the entry count, not the allocated capacity: _activeRuleFrames is always empty when a parse ends, so it keeps the capacity of the deepest recursion, which MaxParseDepth bounds (see Utils.Parser/ROADMAP.md);
  • sequential reuse of an engine, including after a ParserResourceLimitException, produces the same trees as a fresh engine.

Measured before the fix (Release, flat grammar): a CompiledGrammar kept its last input and about 250 MB after a 400,000-token parse until its next call, and a reused ParserEngine kept 119 MB after a 200,000-token parse for as long as it lived; after the fix both retain a few kilobytes, with unchanged timings.

Continuation and shared-prefix ownership boundaries

Ownership view only (limitations remain canonical in companion file):

  • continuation metadata is metadata-only;
  • shared-prefix metadata is metadata-only;
  • lookahead metadata is metadata-only;
  • metadata transport is non-authoritative and discardable.

Mandatory boundaries:

  • metadata does not authorize replay;
  • metadata does not authorize continuation execution;
  • metadata does not authorize branch merging;
  • metadata does not establish semantic equivalence;
  • metadata does not imply rollback safety;
  • metadata does not override diagnostics ownership.

For lifecycle details, anti-feature boundaries, and future activation preconditions, see:

Diagnostics authority boundaries (canonical)

  • ParserEngine is final diagnostics authority.
  • Orchestration diagnostics are non-authoritative.
  • pruning != syntax failure.
  • backtracking observation != syntax failure.
  • metadata transport != diagnostics authority.
  • branch equivalence != parse rejection.
  • trailing-token validation is parser-authoritative.

Observability can exist without authority transfer.

Deterministic observability boundary

Observable runtime artifacts may include scheduler metadata, lookahead observations, continuation/shared-prefix metadata, and branch-state collections. These are testable for auditability but remain non-authoritative.

Incidental internal ordering/layout remains non-contractual unless explicitly documented.

Explicit non-goals (current runtime)

No support for:

  • replay,
  • rollback,
  • execution sharing,
  • branch-merge execution,
  • resumable continuation execution,
  • semantic-aware memoization.

These boundaries are current-contract statements only.

Runtime observation

The optional IParserRuntimeObserver infrastructure is passive and descriptive only. Observer callbacks do not return control decisions and cannot influence scheduling, pruning, parse acceptance, parse-tree shape, or diagnostics authority.

Additional observation contract clarifications:

  • runtime observation ordering is deterministic for a given deterministic parser run;
  • event payloads are immutable descriptive snapshots with explicit event kind and status, not execution handles;
  • observer callback exceptions are isolated by the scheduler and do not alter parser runtime outcomes.
