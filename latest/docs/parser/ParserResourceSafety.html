All-purpose Utilities

Parser Resource Safety (S-06: ETC-16 / ETC-18)

Purpose

Canonical reference for the resource safety of Utils.Parser before an expression tree exists: recursion depth and execution-stack safety (ETC-16), bounded work, bounded node and state growth, and allocation volume (ETC-18). The expression-tree engine budgets of the ETC roadmap (ExpressionResourceLimits) do not cover parsing.

Raw measurements: tests/ExpressionResourceProbe/results/2026-11-19/ (probe: tests/ExpressionResourceProbe/ParserProbe.cs).

1. Recursive call graph

Every recursive path of the runtime goes through one of the following cycles. Method names are those of Utils.Parser/Runtime.

    ParseRule

                -> parseAlternative lambda

    TryParseContent -> TryParseSequence | TryParseQuantifier | TryParseNegation | TryParseAlternative -> TryParseContent

    ParseRule -> ParseLeftRecursiveRule -> TryExtendLeft (loop)

_activeRuleFrames detects re-entry of the same rule at the same token position only. It bounds neither ordinary recursion where successive invocations advance ('(' e ')'), nor recursion through different rule names, nor C2.

Lexer (LexerEngine)

L1  MatchLongest -> TryMatchContent -> ContentMatchers[type]
      -> MatchSequenceContent | MatchAlternationContent | MatchAlternativeContent | MatchQuantifierContent
         | MatchNegationContent | MatchRuleRefContent -> TryMatchContent              (cycle)

_activeRuleRefs blocks the same lexer rule at the same character offset only: a recursive lexer rule such as NEST : '(' NEST? ')' ; recurses once per input character.

Parse-tree consumers

T1  ParseTreeCompiler.Visit -> Visit (one level per tree level)
T2  ParseTreeNavigator.Descendants -> child.Descendants (one nested iterator per tree level)

Guard placement

Every parser cycle (C1, C2, C3) contains ParseRule or TryParseContent; every lexer cycle contains TryMatchContent; T1 contains Visit. Between two consecutive passes through these methods, the number of frames is a constant of the runtime (at most the C1 chain above, about a dozen frames), independent of the grammar and of the input. These methods are therefore the guarded recursion boundaries. Non-guarded recursive helpers (ContainsPredicateOrAction, FindPrecedenceLevel, ParserLookaheadProbe.ProbeContent, structural prefix extraction) recurse over the grammar AST only, never over input, and never follow parser rule references.

3. Resource limits (S-06 design)

Public surface

Type Role
ParserResourceLimits (immutable record) Eight positive limits, Default, Unlimited, validated init setters (ArgumentOutOfRangeException below 1).
ParserResourceLimitException : InvalidOperationException Controlled refusal: Kind, Phase, Limit, Observed (first attempted value over the limit, or the recursion depth for Stack), Offset (input character offset when known). No input text.
ParserResourceLimitKind InputCharacters, Tokens, LexerSteps, LexerDepth, ParseDepth, ParserSteps, ParseNodes, RetainedStates, Stack.
ParserResourcePhase Lexer, Parser, TreeCompilation.
LexerEngine(definition, policy, limits), ParserEngine(definition, policy, limits), CompiledGrammar(definition, policy, limits) Additive constructors; every existing constructor keeps its signature and uses ParserResourceLimits.Default. Each type exposes ResourceLimits.

Generated grammars (XGrammar.Grammar, Parse, ParseWithEmbeddedCode), Antlr4GrammarConverter, SyntaxColorisationGrammar and the CSyntax/VBSyntax front ends use the defaults. A trusted caller that needs more builds its own new CompiledGrammar(XGrammar.Build(), policy, ParserResourceLimits.Unlimited) (or any with variant).

Budget ownership

  • One private ParserResourceBudget per tokenization (created when the Tokenize enumeration starts) and per parse (owned by the per-parse ParseContext). It is never stored in a static, never shared between engines, threads or operations, and is discarded when the operation ends; the engines' internal LastResourceUsage snapshots are diagnostics only.
  • Counters only grow. Backtracking restores token positions and managed semantic state, never consumed budget: steps, nodes and retained states charged by a rejected or pruned branch stay charged.
  • The current depth is restored by finally blocks on every path, so a speculative branch never leaves depth behind.
  • Every check runs before its counter would cross the limit, so no counter overflows (long counters, int depth).
  • Limits never depend on wall-clock time.

What is charged

Dimension Charged at
Lexer step every TryMatchContent dispatch (one per candidate rule at a token start, then one per literal, range, set, rule reference, sequence, alternation, alternative, quantifier iteration, negation, command, action and predicate match attempt). Skipped tokens are charged as steps only.
Lexer depth every active TryMatchContent dispatch (recursive lexer rules and fragments).
Input characters every character read from the TextReader (end of input is not charged); CompiledGrammar also refuses an oversized string before any work.
Tokens every emitted token, any channel, lexer-extension and ERROR tokens included, before it is yielded; and every token supplied directly to ParserEngine.Parse(IEnumerable<Token>), any channel (phase Parser): a list longer than the limit is refused from its count, a lazy sequence before the first token over the limit is examined or stored.
Parser step every ParseRule (memo hits included), every TryParseContent dispatch, every scheduled alternative attempt, every look-ahead probe (preparation and execution), every quantifier iteration attempt, every left-recursive extension attempt. Negation probes are charged through the dispatch of the probed content.
Parse depth every active ParseRule and TryParseContent (rule invocations and content nesting alike).
Parse nodes every ParserNode, QuantifierNode and LexerNode built by the engine, empty predicate/action nodes included, in accepted and rejected branches alike.
Retained states every new visited-state key, continuation entry, completed (memoized) result and look-ahead cache entry, charged before insertion. A refused insertion stores nothing and refuses the whole parse; nothing is evicted or silently dropped, so cached results never change meaning.

Stack guard

RuntimeHelpers.TryEnsureSufficientExecutionStack() runs at every guarded recursion boundary (ParseRule, TryParseContent, TryMatchContent, ParseTreeCompiler.Visit). Between two boundaries the runtime executes a bounded number of frames (section 1), so the guard's fixed headroom covers them. StackOverflowException is never caught. The guard cannot be disabled. ParseTreeNavigator.Descendants() was converted to an explicit-stack traversal (same depth-first pre-order) so it no longer nests one iterator per tree level.

Exception and state semantics

  • A refusal is never a syntax error: it is not converted into an ErrorNode, no truncated tree is returned.
  • Exceptions thrown by injected policies (predicate evaluators, action executors, state managers, lifecycle executors, frame managers, rule-call policies, lexer extensions) propagate unchanged; they are never wrapped into a refusal.
  • On a refusal every entered invocation frame is exited (Exit), every rule call gets AfterRuleCall, the active rule-frame set and the lexer's active rule references are released by the existing finally blocks, and the parse's registry, memo and look-ahead state is cleared. The next operation on the same engine starts clean.
  • Lifecycle change: registry, memo and look-ahead state is now released when every parse ends, not only when the next parse starts. Before S-06 a long-lived engine (for example the shared CSyntax grammar) kept the state of its last parse alive (437 MB after the historical 20,000-term input).
  • Limits count parser-managed work only. They cannot interrupt user code running inside a policy callback; such code is charged only for the parser work it causes. No Thread.Abort, asynchronous cancellation or broad catch is used.

4. Default thresholds and rationale

Limit Default Rationale (measured)
MaxInputCharacters 1,000,000 Coarse input-size bound; the historical 20,000-term input has 168,887 characters.
MaxTokens 500,000 At most one token per character in practice; 12.5 times the historical input's 39,999 tokens.
MaxLexerSteps 50,000,000 CSyntax needs about 14.5 steps per character (2.45 M for the historical input), so ordinary input meets MaxInputCharacters first; quadratic lexer patterns are stopped after a few thousand characters.
MaxLexerDepth 4,000 Ordinary tokens need depth 4 to 5; a recursive lexer rule needs about 4 levels per nesting level, so 4,000 accepts about 1,000 nested levels (the Windows 1 MiB stack guard refuses at about 2,600).
MaxParseDepth 4,000 One right-recursive rule level costs 3 depth units, one CSyntax parenthesis level about 33. On Windows 1 MiB stacks the stack guard refuses first (about 620–665 units: CSyntax 19 pairs accepted in Release, baseline crashed at 20); on Linux 8 MiB main threads the stack guard would refuse at about 4,100–4,350 units, so 4,000 makes that refusal deterministic while keeping the baseline capacity (CSyntax 110 pairs accepted; baseline crashed at 150).
MaxParserSteps 10,000,000 The historical input needs 3.94 M steps (about 98 per token).
MaxParseNodes 5,000,000 The historical input builds 260,021 nodes, failed branches included.
MaxRetainedStates 5,000,000 The historical input retains 3.0 M states (about 75 per token, about 145 bytes each before S-06), which bounds the live registry memory of one parse.

7. Shared-grammar concurrency (issue #709)

Defect

CSyntaxTokenParser and VBSyntaxTokenParser share one lazily-initialized static CompiledGrammar per dialect, and every generated grammar class shares one static Grammar. Before #709 a CompiledGrammar owned a single LexerEngine and a single ParserEngine, whose per-operation state (_activeRuleFrames, the ParserStateRegistry visited states, continuations and memoized results, the ParserLookaheadCache, the lexer mode stack, pending more text and active rule references) was cleared and refilled by every call. Concurrent calls cleared each other's state, selected memoized results computed for another input, and corrupted the non-thread-safe collections themselves. The S-06 probe (ExpressionResourceProbe parser-concurrency 8 400) first measured it on e0013a11 and S-06: 818–893 silently corrupted trees and 668–730 exceptions out of 3,200 operations.

Reproduction campaign

ExpressionResourceProbe parser-concurrency-campaign (see tests/ExpressionResourceProbe/README.md) compares every concurrent result with a sequential oracle computed on fresh CompiledGrammar instances: canonical tree rendering (node types, rule names, modes, spans with line and column, token rule/channel/text, error messages), full token metadata, refusal classification (kind, phase, limit, observed value, offset) and, for the compile surfaces, the values of the compiled delegate. Seven surfaces (CSyntax and VBSyntax token parsers, the generated static CSyntax grammar, a shared ANTLR4 grammar with lexer modes, more, a hidden channel and left recursion, the same grammar under tight limits, and shared CSyntax/VBSyntax expression compilers), three workloads (parse, tokenize, mixed), 2/4/8/16 dedicated threads re-synchronized by a barrier every 25 operations, deterministic per-worker seeds, one process per surface. Fix

Every Tokenize / Parse call now creates its own LexerEngine and ParserEngine over two internal preparations built once by the CompiledGrammar constructor and never mutated: LexerEngine.Preparation (case sensitivity, keyword trie and candidate rules of every mode) and ParserEngine.Preparation (scheduling shapes keyed by alternative-list reference, stable priority order). The grammar model is immutable (immutable arrays and init-only records), so sharing the preparations cannot make them stale. No lock, ThreadLocal, pool or static mutable state is used, the public constructors of the engines build their own preparation as before, and the internal CompiledGrammar.Lexer / Parser diagnostic accessors return the engines of the last call that started. Each operation still owns its S-06 budget; SharedGrammarResourceIsolationTests (Security) checks that concurrent refusals on one shared grammar keep their exact classification and that an operation after a refusal starts from a clean budget. Ownership table: RuntimeStateOwnership.md.

8. Remaining limitations and follow-up

  • Small stacks are not supported for useful work. The parser guarantees a controlled refusal, not successful parsing, on small stacks: on a 256 KiB thread even (x0) is refused by CSyntax/VBSyntax and Antlr4GrammarConverter refuses small grammar texts. Run parsing on threads of at least 1 MiB (the .NET default on Windows) when inputs must succeed.
  • Stack capacity. About 1.3 KB of stack per depth unit (Windows Release): a 1 MiB thread accepts 19 CSyntax parenthesis levels and a 256 KiB thread accepts unparenthesized CSyntax expressions but refuses (x0) (the baseline parsed 2 levels there and crashed at 3: the guard's fixed headroom, reserved by TryEnsureSufficientExecutionStack, costs the remaining capacity of very small stacks); the ANTLR4 meta-grammar used by Antlr4GrammarConverter is refused (controlled Stack) on a 256 KiB thread even for small grammar texts. These are controlled refusals, not crashes; raising capacity needs fewer frames per recursion cycle or an explicit-stack execution model (not attempted: it would replace the parser execution model).
  • Exception filters. A ParserResourceLimitException of kind Stack is thrown with only the guard's headroom left. catch blocks run after unwinding and are safe; an exception filter (catch ... when (...)) on the caller's side runs before unwinding, on the nearly exhausted stack: keep such filters trivial (the S-06 probe was itself caught by this).
  • Allocation. Parsing remains linear at about 20 KB allocated per input character (CSyntax compile). Since the registry-metadata audit (section 9) the registry is stored compactly, and since the look-ahead cache audit (section 10) so is the look-ahead cache, whose remaining share is mostly one expected-name collection per entry; the write-only registry metadata (visited states, continuations) is still stored and charged, because removing it changes the RetainedStates accounting (section 9, "Contract change not made").
  • Grammar immutability assumption. ParserEngine precomputes scheduling shapes (priority order, structural descriptors) and LexerEngine precomputes candidate rules and keyword tries from the definition, once per CompiledGrammar (shared by the engines of every call, #709) or once per directly constructed engine. This relies on the documented immutability of the grammar model (Rule, Alternation, LeftRecursiveRuleInfo capture immutable snapshots); a future mutable model would have to invalidate these tables.
  • Wall-clock time and process memory are not limited; the budgets bound parser-managed work and retained states.
  • User code inside policy callbacks is not interrupted and not covered by the stack guard beyond its headroom.
  • Concurrency: shared grammars are safe since #709 (section 7); the per-call engines cost 12–19 % more parse allocation than a reused engine, and directly constructed engines and stateful policy components remain caller-owned.

9. Registry metadata storage (registry-metadata audit)

Question and audit

ParserStateRegistry held three collections whose memory was proportional to the parse: visited states, continuations and completed (memoized) results. The audit (producer/consumer matrix in RuntimeStateOwnership.md, section "Registry usage audit and compact storage") establishes, from the code of 6e7892a0:

  • visited states are written by every scheduled attempt and every left-recursive extension attempt and never read in production (both callers ignore the result; the left-recursion cycle rejection uses a local set);
  • continuations are written for every rule reference, lexer tokens included, and never read in production;
  • completed results are the memoization: read by every ParseRule, they carry the post-rule execution-state snapshots restored on memo hits. In production each invocation key stores exactly one result;
  • each new entry of the three collections and of the look-ahead cache costs one RetainedStates unit, charged before insertion; duplicates are free. A duplicate can only be recognized if the entry is kept, so every write-only entry still matters to S-06: it is the condition under which later identical writes are not charged.

Strategies studied

Strategy Result
A. Compact exact structures Retained. Same identities, same deduplication, same charges and refusals, less memory (below).
B. Charge without materializing Not possible exactly: without the entry, a later duplicate cannot be recognized, so it would be charged (or never charged, with a counter per attempt). Exact deduplication without storing the full key needs a hash standing for the identity, which is excluded. B therefore reduces to A.
C. Optional materialization Not materializing visited states or continuations by default changes the RetainedStates counts (see below): a contract change, not made here.
D. Removing the unused writes No production read, no diagnostic and no policy depends on the two write-only collections; their only effect is their S-06 charge. Removing them is the same contract change as C.

Strategy A, as implemented (ParserStateRegistry remarks):

  • visited states whose element index equals their alternative index (every key the engine records) and whose alternative index is in [0, 63] are grouped by (rule, position, precedence) in one dictionary entry with one bit per alternative; any other key is kept whole in an overflow set. The partition depends on the key alone, so a key is always looked up where it would be stored;
  • continuations are one flat set of (invocation, continuation) pairs instead of one nested set per invocation (a nested set holding a single pair cost about 200 bytes);
  • completed results keep their first result inline in the dictionary value, with an overflow list only for later results of the same key, which the engine never stores (a one-element List cost about 150 bytes per memoized invocation).

Rule names keep string value equality, as before (no interning, no reference identity), and no hash stands for an identity; there is no shared or static storage, so concurrent and sequential engines are unaffected.

Method

Probe ExpressionResourceProbe parser-registry (see tests/ExpressionResourceProbe/README.md): one scenario per process on a directly constructed ParserEngine, warm-up on the same input. --peak forces a full collection when the root rule invocation exits, the last point where every per-parse collection is complete (the engine clears them right after), and reports the managed live bytes released by the end of the parse (peakRegistry = live at root exit − live after the parse). Timing runs omit --peak and report the median of 7 parses. Tree, diagnostics and action/predicate trace are digested (SHA-256) for the differential comparison. Windows 11, .NET 8.0.34, Release; base 6e7892a0 built from a separate worktree with the same probe sources; campaigns in the order base, branch, branch, base.

Scenarios: CSyntax and VBSyntax sums (1,000 and 5,000 terms), mixed CSyntax/VBSyntax expressions (calls, members, indexers, products, logical comparisons; 1,000 terms), CSyntax parentheses (15 pairs), 20 keyword-led alternatives (2,000 items), common prefixes with backtracking (2,000 items), a highly ambiguous grammar (150 tokens), left recursion (2,000-term sum; 1,000 terms with two precedence levels), a deep rule chain (300 levels), and a grammar with actions and semantic predicates driven by a counter execution state whose key changes with every action (1,000 items: memo hits restore snapshots). Every scenario runs with and without diagnostics, and refusals are measured at the exact threshold (N accepted, N − 1 refused) and far below it.

Contract change not made (separate proposal)

After strategy A, the two write-only collections hold 5.8 MB of the 24.7 MB peak above (24 %) and 162,154 of the 300,279 charged retained states (54 %). Not recording them in production (strategies C/D) would:

  • lower RetainedStates for the same input (CSyntax 2,000 terms: 300,279 → 138,125), so MaxRetainedStates would refuse later and at other offsets, and every documented threshold and refusal measurement would move;
  • remove the observations returned by the internal GetContinuations and the visited-state counts (tests only, no production consumer);
  • change neither trees, diagnostics nor actions (no production read).

Such a change needs its own PR: an explicit decision on the meaning of MaxRetainedStates (and possibly a lower default, to keep the same memory bound), an opt-in metadata recording for tools that read continuations, and new threshold measurements. The look-ahead cache, then the largest per-parse collection, received the same kind of compact exact storage in a later change (section 10).

10. Look-ahead cache storage (look-ahead cache audit)

Question and audit

After section 9 the ParserLookaheadCache was the largest per-parse collection (CSyntax 1,000-term sum: 7.98 of 12.66 MB of parse-scoped memory). The producer/consumer matrix is in RuntimeStateOwnership.md, section "Look-ahead cache usage audit and compact storage". In short: two paths read the cache before probing (SchedulingPreparation, ScheduledAlternativeExecutor), a hit replaces a probe and its step charge, a new entry costs one RetainedStates unit charged before insertion, duplicates are free and never replace the first value. Production consumers read the kind and the expected-token names only, but the tests compare results by record equality, so the cache must return the same kind, token-string instances and expected-name collection instance.

Strategies studied

Strategy Result
A. Grouping by (rule, position, precedence, cursor kind, cursor index) with a per-group alternative mask Not retained. Half of the CSyntax groups hold a single entry and each group still needs one (kind, collection) slot per alternative, so a per-group array (24-byte header, regrown as alternatives arrive) replaces the per-entry key. Estimated from the distributions above: CSyntax mixed about 11.3 MB against 11.7 MB for D below, with one allocation per group and a regrowth per new alternative; only grammars with wide groups (20 alternatives: about 0.8 instead of 2.7 MB) would gain. Not prototyped.
B. Compact values Retained in part. The token snapshot is stored once per origin position (index in a per-cache table, a separate snapshot when an entry's instances differ) and the kind in 8 bits. The expected-name collection instance is kept: replacing it by a shared or rebuilt instance changes the instance returned (and allocates a box per hit if rebuilt).
C. Numeric identities for repeated strings Retained. Rule names map to a per-cache index (ordinal comparison, at most 1,024, null or overflow goes to the exact overflow store), the four ScheduledAlternativeCursorKinds to a 2-bit code; any other cursor kind is stored unchanged. Tables cost about 3 KB on CSyntax and are emptied by Clear(); no global or shared table.
D. Minimal dictionary optimization Retained as the base layout: one Dictionary keyed by a 64-bit packed key (32-bit origin, 8-bit alternative, 10-bit rule index, 2-bit cursor kind, 6-bit precedence, 6-bit cursor index + 1) with a multiplicative hash, values of 16 bytes: 36 bytes per slot instead of 76. Packing the key while keeping the full 32-byte value would cost 52 bytes per slot (CSyntax sum 1,000: 3.92 instead of 2.72 MB). CollectionsMarshal.GetValueRefOrAddDefault was not used: it inserts before the S-06 charge and would need a removal on refusal; the frequent duplicate path already costs a single lookup.

Remaining (separate proposal)

The expected-name collections are now about 45 % of the cache (CSyntax sum 1,000: 2.24 of 5.07 MB), with one instance per entry for fewer than 70 distinct values. ParserLookaheadProbe builds a new collection on every probe (the shallow expected-name list, then the ImmutableArray copy and its box). Returning one instance per alternative content would remove that memory and those allocations without changing any value, any probe kind or any S-06 charge, but two results from different probes would then share their collection and compare equal by reference where they did not, and the probe would hold per-engine state. It is a change of the probe, not of the cache, and is left to a separate PR. No other compaction was found that keeps the stored instances.
