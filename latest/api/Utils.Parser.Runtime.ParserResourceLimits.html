Remarks

Every operation owns a private budget created when it starts and discarded when it ends, successfully or not. Counters are never shared between operations, engines, threads or processes, and a failed operation never leaves budget state behind. Limits are deterministic work and size bounds: none of them depends on wall-clock time.

Lexer limits (MaxInputCharacters, MaxTokens, MaxLexerSteps, MaxLexerDepth) bound a tokenization, including the tokenization performed by Parse(string). Parser limits (MaxParseDepth, MaxParserSteps, MaxParseNodes, MaxRetainedStates) bound the parse of a token stream. Exceeding any limit ends the operation with a ParserResourceLimitException; it is never reported as a syntax error and never produces a truncated parse tree.

Independently of these limits, every recursive lexer, parser and parse-tree-compilation step checks the remaining execution stack. When the stack is insufficient, the operation ends with a ParserResourceLimitException of kind Stack instead of a process-terminating stack overflow. This guard cannot be disabled, not even by Unlimited.

Limits count parser-managed work only. They cannot interrupt user code running inside a custom runtime policy (semantic predicate evaluator, action executor, state manager, lifecycle executor, rule-call policy, observer, or lexer extension); such code is charged only for the parser work it causes.

MaxTokens

Gets the maximum number of tokens one tokenization emits, every channel and lexer-extension token included. Skipped tokens are not emitted and are charged as lexer steps only. The same limit bounds the tokens supplied directly to Parse(IEnumerable<Token>, Rule?, DiagnosticBag?): every received token counts, whatever its channel; a list longer than the limit is refused before it is examined, and a lazy sequence is refused before the first token over the limit is examined or stored (kind Tokens, phase Parser).
