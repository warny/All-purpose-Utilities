Remarks

Contract. An optimized tree has exactly the type of its source and, once compiled, produces the same value (the same bits for binary floating point, signed zeros and NaN payloads included, except that the hardware may quiet a signaling NaN) or the same exception, with the same evaluations in the same order. A rule that cannot prove this for the node it inspects leaves the node unchanged. The rules and their guards are listed in docs/expressions/ExpressionOptimiser.md:

  • x + 0, 0 + x, x - 0, x * 1, 1 * x, x / 1 on primitive integral and binary floating-point arithmetic without operator method (lifted forms included); for floating point the zero must have the neutral sign (x + (-0.0), x - (+0.0));
  • x * 0 and 0 * x on non-lifted primitive integral arithmetic, when the dropped operand is proven discardable by Utils.Expressions.ExpressionEffectAnalysis;
  • -(-x) on primitive unchecked negation, and identity conversions without method;
  • constant short circuits of bool and lifted Nullable<T> of bool operators without method, and constant conditions whose selected branch has the conditional's type and whose discarded branch defines no label;
  • removal of the Default(void) statements of a block other than its last one, and unwrapping of a block holding a single expression of its own type and no variable.

Custom operator and conversion methods, checked arithmetic, decimal arithmetic, quoted expressions and extension nodes are never rewritten. No user code runs: no node is evaluated, no reflection object of the tree is read (the methods are only compared with null), and an extension node is passed through without any call into it (ETC R4).

Resources. Each call is one operation of the shared expression resource session: the input is validated against ResourceLimits (depth and logical nodes) before any work, every node, binding, initializer, switch case and catch block visited counts one structural visit, and every recursion is stack-guarded, so a hostile input ends with an ExpressionResourceLimitException instead of a stack overflow. A shared subtree is walked once per use, like every walk of the engine.

Tracing. Inside a tracing scope (ExpressionTransformTracing) every node visited is a treatment of the trace, reported for ExpressionOptimiser: its enter event, the rule that rewrote it if any (a RuleApplied event whose input is the source node), and its exit with the outcome (Unchanged, Rebuilt, RuleApplied, or Boundary for a quote), or its failure. The detailed level adds no event: the optimiser has no candidate rules nor lexical scopes to report. The optimization itself is unchanged, and outside a scope the only cost is one field read per call (no allocation).
